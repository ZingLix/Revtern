# Connector Design

## Connector Goals

Each connector should:

- Ingest source events safely and idempotently.
- Preserve raw source payloads.
- Verify authenticity where possible.
- Normalize source semantics into Revtern events.
- Expose webhook health and setup status in the UI.

Connectors should not directly write dashboard metrics. They should write raw
events and enqueue normalization/projection jobs.

## Connector Interface

Backend connector responsibilities:

```text
verify_webhook(request) -> VerifiedPayload
extract_event_identity(payload) -> SourceEventIdentity
store_raw_event(identity, payload) -> RawEvent
normalize(raw_event) -> NormalizedEvent[]
catch_up_notifications(source, window) -> CatchUpRun
health_check(source) -> SourceHealth
```

For the MVP, every source event must enter as a webhook-shaped notification.
Catch-up is allowed only to recover missed webhook notifications from provider
notification history or message backlog. Connectors must not call purchase
status APIs, import financial reports, or enrich transactions outside the
webhook payload.

## App Store Connector

### Inputs

- App Store Server Notifications V2.

### Setup Data

Required:

- Bundle id.
- Shared webhook URL generated by Revtern.
- Optional App Store Server API key for notification-history catch-up.

### Webhook Flow

1. Apple posts notification to Revtern webhook URL.
2. Revtern verifies signed payload.
3. Revtern extracts notification type, subtype, transaction id, original
   transaction id, bundle id, product id, and event time.
4. Revtern inserts a `raw_events` row.
5. Revtern enqueues normalization.

MVP implementation status:

- App Store notifications are accepted at `/webhooks/app-store/{source_id}`.
- `signedPayload` compact JWS payloads are decoded.
- Nested `data.signedTransactionInfo` and `data.signedRenewalInfo` JWS payloads
  are decoded for product, transaction, amount, and lifecycle fields.
- The original notification body remains in `raw_events.payload`.
- Full Apple certificate-chain validation is not complete yet, so production
  deployments should keep the webhook endpoint private until that hardening is
  finished.

### Catch-Up Flow

1. User starts catch-up for an App Store source.
2. Revtern calls App Store notification history for a time window.
3. Each returned `signedPayload` is stored as `{ "signedPayload": "..." }`.
4. The payload enters the same raw event and normalization path as live
   webhooks.

Catch-up must not call transaction history, subscription status, or sales
reports.

### Normalized Events

Example mappings:

- `SUBSCRIBED` -> `purchase` or `trial_started`.
- `DID_RENEW` -> `renewal`.
- `DID_CHANGE_RENEWAL_STATUS` -> `cancellation` when auto-renew is disabled.
- `EXPIRED` -> `expiration`.
- `REFUND` -> `refund`.
- `GRACE_PERIOD_EXPIRED` -> `expiration` or `billing_issue`.

Mapping must be versioned because store semantics can be subtle.

## Google Play Connector

### Inputs

- Real-time Developer Notifications through Google Cloud Pub/Sub.

### Setup Data

Required:

- Package name.
- Google Cloud project id.
- Pub/Sub topic/subscription setup.
- Revtern webhook endpoint for Pub/Sub push.
- Optional Pub/Sub pull credentials for missed-RTDN catch-up.

### RTDN Flow

1. Google Pub/Sub sends push message to Revtern.
2. Revtern verifies the push source according to configured deployment mode.
3. Revtern decodes the Pub/Sub message.
4. Revtern extracts package name, notification type, purchase token, and event
   time.
5. Revtern stores the Pub/Sub payload in `raw_events`.
6. Revtern enqueues normalization.

MVP implementation status:

- Pub/Sub push payloads are accepted at `/webhooks/google-play/{source_id}`.
- The base64 `message.data` field is decoded into a `DeveloperNotification`.
- The original Pub/Sub payload remains in `raw_events.payload`.
- RTDN does not include price by default; revenue can only use amount fields
  included in the webhook payload.

### Catch-Up Flow

1. User starts catch-up for a Google Play source.
2. Revtern pulls retained messages from the configured Pub/Sub subscription.
3. Each pulled message is wrapped in the same Pub/Sub push body shape and stored
   as a raw event.
4. After storing the payloads, Revtern acknowledges the Pub/Sub messages.

Catch-up must not call Google Play purchase status APIs. If Pub/Sub has already
discarded the missed message, Revtern does not try to reconstruct it from
purchase tokens or financial reports.

### Normalized Events

Example mappings:

- subscription purchased -> `purchase` or `trial_started`.
- subscription renewed -> `renewal`.
- subscription canceled -> `cancellation`.
- subscription expired -> `expiration`.
- subscription revoked -> `refund` or `revoked` transaction status.
- subscription in grace period -> `grace_period_started`.
- subscription on hold -> `billing_issue`.
- subscription recovered -> `billing_issue_resolved`.

## RevenueCat Connector

### Inputs

- RevenueCat webhooks.

### Setup Data

Required:

- RevenueCat project/app id where useful.
- Webhook authorization header or shared secret.

### Webhook Flow

1. RevenueCat sends webhook to Revtern.
2. Revtern verifies authorization.
3. Revtern stores raw event.
4. Revtern normalizes event into Revtern lifecycle events.

RevenueCat is a good first connector because it gives a useful cross-platform
event stream without forcing Revtern to implement all store edge cases on day
one.

### Important Caveat

RevenueCat data may overlap with App Store and Google Play webhook data. If a
developer connects both RevenueCat and store webhooks, Revtern must prevent
double-counting by linking events through transaction ids, original transaction
ids, purchase tokens, product ids, and event time windows.

## Stripe Connector

Webhook connector for web subscriptions and one-time purchases.

Inputs:

- Stripe webhooks.

Normalized entities:

- Customer.
- Subscription.
- Invoice.
- Payment intent or charge.
- Refund.

Stripe should map naturally to SaaS-style MRR, but app-store semantics differ.
Revtern should preserve source differences instead of forcing all billing
systems into one simplistic model.

## Paddle Connector

Webhook connector for web-to-app monetization.

Inputs:

- Paddle webhooks.

Important fields:

- Customer id.
- Subscription id.
- Transaction id.
- Product/price id.
- Tax and fee data where available.

## CSV Connector

CSV import is outside the webhook-notification MVP. If it returns later, it
should be treated as an explicit import source, not as hidden notification
catch-up.

## Custom API Connector

A simple ingestion endpoint for developers with their own backend.

Example event:

```json
{
  "event_id": "evt_123",
  "event_type": "purchase",
  "occurred_at": "2026-06-30T08:00:00Z",
  "app_id": "my-app",
  "product_id": "pro_monthly",
  "transaction_id": "txn_123",
  "customer_id": "user_123",
  "amount_minor": 999,
  "currency": "USD",
  "country": "US"
}
```

This makes Revtern useful even before every official connector is implemented.

## Connector Priority

Recommended build order:

1. RevenueCat webhook.
2. Custom API webhook.
3. App Store Server Notifications.
4. Google Play RTDN.
5. Stripe webhook.
6. Paddle webhook.
7. Adapty/Apphud/Qonversion webhooks if user demand appears.
