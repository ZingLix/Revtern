# Connector Design

## Connector Goals

Each connector should:

- Ingest source events safely and idempotently.
- Preserve raw source payloads.
- Verify authenticity where possible.
- Normalize source semantics into Revtern events.
- Expose webhook health and setup status in the UI.

Connectors should not directly write dashboard metrics. They should write raw
events and enqueue normalization/projection jobs.

## Connector Interface

Backend connector responsibilities:

```text
verify_webhook(request) -> VerifiedPayload
extract_event_identity(payload) -> SourceEventIdentity
store_raw_event(identity, payload) -> RawEvent
normalize(raw_event) -> NormalizedEvent[]
catch_up_notifications(source, window) -> CatchUpRun
health_check(source) -> SourceHealth
```

For the MVP, every source event must enter as a webhook-shaped notification.
Catch-up is allowed only to recover missed webhook notifications from provider
notification history or message backlog. Connectors must not call purchase
status APIs for historical backfill, import financial reports, or enrich
transactions outside the webhook payload. The only exception is Google Play
environment verification: after an RTDN arrives, Revtern may call the Android
Publisher purchase endpoint for that purchase token to decide whether the order
is production or test.

## App Store Connector

### Inputs

- App Store Server Notifications V2.

### Setup Data

Required:

- Bundle id, read from the selected Revtern app.
- Shared webhook URL generated by Revtern.
- Expected environment; production sources also require the numeric app Apple
  id.
- Optional App Store Server API key for one-click test notifications and
  notification-history catch-up.

Revtern bundles Apple's published root certificates for JWS verification. Users
do not need to download certificates or construct credentials JSON. The source
form collects the app Apple id and keeps notification-history credentials in an
optional advanced section.

When an In-App Purchase key is configured, the source card can request a signed
`TEST` notification from either Apple's sandbox or production App Store Server
API. Revtern generates the short-lived ES256 JWT on the server; private key
material is never returned to the browser. Apple's request token is shown after
the request is accepted, and the normal setup checklist updates when the signed
callback arrives.

### Webhook Flow

1. Apple posts notification to Revtern webhook URL.
2. Revtern verifies signed payload.
3. Revtern extracts notification type, subtype, transaction id, original
   transaction id, bundle id, product id, and event time.
4. Revtern inserts a `raw_events` row.
5. Revtern enqueues normalization.

MVP implementation status:

- App Store notifications are accepted at `/webhooks/app-store/{source_id}`.
- `signedPayload` compact JWS payloads are verified and decoded.
- The JWS `x5c` chain is validated against the configured Apple root, and the
  ES256 signature, bundle id, environment, and production app Apple id are
  checked before the raw event is accepted.
- Nested `data.signedTransactionInfo` and `data.signedRenewalInfo` JWS payloads
  are separately verified and decoded for product, transaction, amount, period,
  and lifecycle fields.
- Notification and transaction `environment` fields are normalized to
  `production`, `sandbox`, or `unknown` and stored on every event and projected
  order.
- The original notification body remains in `raw_events.payload`.
- Invalid or unconfigured signatures return `401` and are not stored.

### Catch-Up Flow

1. User starts catch-up for an App Store source.
2. Revtern calls App Store notification history for a time window.
3. Each returned `signedPayload` is stored as `{ "signedPayload": "..." }`.
4. The payload enters the same raw event and normalization path as live
   webhooks.

Catch-up must not call transaction history, subscription status, or sales
reports.

### Normalized Events

Example mappings:

- `SUBSCRIBED` -> `purchase` or `trial_started`.
- `DID_RENEW` -> `renewal`.
- `DID_CHANGE_RENEWAL_STATUS` -> `cancellation` when auto-renew is disabled.
- `EXPIRED` -> `expiration`.
- `REFUND` -> `refund`.
- `GRACE_PERIOD_EXPIRED` -> `expiration` or `billing_issue`.

Mapping must be versioned because store semantics can be subtle.

## Google Play Connector

### Inputs

- Real-time Developer Notifications through Google Cloud Pub/Sub.

### Setup Data

Required:

- Package name, read from the selected Revtern app.
- Google Cloud project id.
- Pub/Sub topic/subscription setup.
- Revtern webhook endpoint for Pub/Sub push.
- Push authentication service account email. Revtern derives the expected OIDC
  audience from its generated webhook URL.
- Optional Pub/Sub pull credentials for missed-RTDN catch-up.
- Optional Android Publisher API access on the same service account for
  purchase environment verification.

The source form accepts the downloaded service account JSON as a file upload;
users do not construct credentials JSON. The file can provide Android Publisher
API access on its own, while adding the Pub/Sub subscription path also enables
missed-RTDN catch-up. Revtern encrypts the parsed credentials before storage.

### RTDN Flow

1. Google Pub/Sub sends push message to Revtern.
2. Revtern verifies the push source according to configured deployment mode.
3. Revtern decodes the Pub/Sub message.
4. Revtern extracts package name, notification type, purchase token, and event
   time.
5. Revtern stores the Pub/Sub payload in `raw_events`.
6. Revtern enqueues normalization.

MVP implementation status:

- Pub/Sub push payloads are accepted at `/webhooks/google-play/{source_id}`.
- Authenticated pushes are verified locally against Google's public OIDC signing
  keys; issuer, audience, expiry, service-account email, and `email_verified`
  must match. Signing keys are cached using Google's `Cache-Control` lifetime and
  refreshed after expiry or when Google rotates to a new key id.
- The base64 `message.data` field is decoded into a `DeveloperNotification`.
- `testNotification` messages are marked as `test`.
- Purchase RTDNs are marked `production` or `test` only after Revtern can call
  Google Play Developer API with the purchase token.
- If Android Publisher API access is missing or denied, the purchase is marked
  `unknown`; unknown purchases are excluded from production revenue metrics.
- The original Pub/Sub payload remains in `raw_events.payload`.
- RTDN does not include price by default; revenue can only use amount fields
  returned by Android Publisher lookup or explicitly included in a custom payload.
- Subscription renewals use the Play order id returned by Publisher lookup, so
  multiple charges sharing one purchase token remain separate ledger entries.

### Webhook Diagnostics

At the default `revtern_api=info` log level, each live webhook receives a
`whreq_*` request id and logs the major processing stages: request receipt, JSON
parsing, source lookup, authentication method, package verification, provider
lookup, raw-event storage, deduplication, normalization, and completion or
failure. Google OIDC key refreshes log their reason, proxy availability,
duration, cache lifetime, and a timeout/connect classification on failure.
Bearer tokens, private keys, complete payloads, and purchase tokens are never
written to these diagnostic logs. Cache-hit details remain at debug level.

Google uses the same RTDN webhook path for test and production purchase
notifications. RTDN tells Revtern that a purchase changed, but it does not
contain complete purchase details. To classify a purchase, Revtern calls:

- `purchases.subscriptionsv2.get` for subscription RTDNs and checks whether
  `testPurchase` is present.
- `purchases.productsv2.getproductpurchasev2` for one-time product RTDNs and
  checks whether `testPurchaseContext` is present.

The service account needs Play Console access to the app and the OAuth scope
`https://www.googleapis.com/auth/androidpublisher`. Pub/Sub subscriber access
alone can still receive webhooks and pull missed RTDNs, but cannot verify
whether a purchase token is real or test.

### Catch-Up Flow

1. User starts catch-up for a Google Play source.
2. Revtern pulls retained messages from the configured Pub/Sub subscription.
3. Each pulled message is wrapped in the same Pub/Sub push body shape and stored
   as a raw event.
4. After storing the payloads, Revtern acknowledges the Pub/Sub messages.

Catch-up pulls only retained Pub/Sub RTDN messages. After a missed RTDN is
pulled, the same purchase environment verification may run for that token. If
Pub/Sub has already discarded the missed message, Revtern does not try to
reconstruct it from financial reports or unrelated purchase histories.

### Normalized Events

Example mappings:

- subscription purchased -> `purchase` or `trial_started`.
- subscription renewed -> `renewal`.
- subscription canceled -> `cancellation`.
- subscription expired -> `expiration`.
- subscription revoked -> `refund` or `revoked` transaction status.
- subscription in grace period -> `grace_period_started`.
- subscription on hold -> `billing_issue`.
- subscription recovered -> `billing_issue_resolved`.

## RevenueCat Connector

### Inputs

- RevenueCat webhooks.

### Setup Data

Required:

- RevenueCat project/app id where useful.
- Webhook authorization header or shared secret.

### Webhook Flow

1. RevenueCat sends webhook to Revtern.
2. Revtern verifies authorization.
3. Revtern stores raw event.
4. Revtern normalizes event into Revtern lifecycle events.

RevenueCat is a good first connector because it gives a useful cross-platform
event stream without forcing Revtern to implement all store edge cases on day
one.

### Important Caveat

RevenueCat data may overlap with App Store and Google Play webhook data. If a
developer connects both RevenueCat and store webhooks, Revtern must prevent
double-counting by linking events through transaction ids, original transaction
ids, purchase tokens, product ids, and event time windows.

## Stripe Connector

Webhook connector for web subscriptions and one-time purchases.

Inputs:

- Stripe webhooks.

Normalized entities:

- Customer.
- Subscription.
- Invoice.
- Payment intent or charge.
- Refund.

Stripe should map naturally to SaaS-style MRR, but app-store semantics differ.
Revtern should preserve source differences instead of forcing all billing
systems into one simplistic model.

## Paddle Connector

Webhook connector for web-to-app monetization.

Inputs:

- Paddle webhooks.

Important fields:

- Customer id.
- Subscription id.
- Transaction id.
- Product/price id.
- Tax and fee data where available.

## CSV Connector

CSV import is outside the webhook-notification MVP. If it returns later, it
should be treated as an explicit import source, not as hidden notification
catch-up.

## Custom API Connector

A simple ingestion endpoint for developers with their own backend.

Example event:

```json
{
  "event_id": "evt_123",
  "event_type": "purchase",
  "occurred_at": "2026-06-30T08:00:00Z",
  "app_id": "my-app",
  "product_id": "pro_monthly",
  "transaction_id": "txn_123",
  "customer_id": "user_123",
  "amount_minor": 999,
  "currency": "USD",
  "country": "US"
}
```

This makes Revtern useful even before every official connector is implemented.

## Connector Priority

Recommended build order:

1. RevenueCat webhook.
2. Custom API webhook.
3. App Store Server Notifications.
4. Google Play RTDN.
5. Stripe webhook.
6. Paddle webhook.
7. Adapty/Apphud/Qonversion webhooks if user demand appears.
